# DeepSeek 对话导出 Markdown

## 获取 1.5.8

适用于 Microsoft Edge 等 Chromium 内核浏览器，开源许可为 MIT。

1. 在 [Releases](https://github.com/LIAN666666101/deepseek-chat-exporter/releases/latest) 下载 `deepseek-md-exporter-v1.5.8.zip` 并解压。
2. Edge 打开 `edge://extensions/`，Chrome 打开 `chrome://extensions/`，启用「开发人员模式」。
3. 点击「加载解压缩的扩展」，选择解压后包含 `manifest.json` 的文件夹。
4. 刷新 DeepSeek 对话页，点击右下角「导出 MD」，选择 Markdown、Word 或 PDF。
5. 按需点击「选择消息」。勾选一条时导出单条，勾选多条时导出最小编号到最大编号之间的全部消息。

PDF 使用浏览器打印窗口保存。请将目标设为「另存为 PDF」，关闭浏览器的「页眉和页脚」。

### 数据处理与兼容范围

文件解析与生成在浏览器本地完成。默认模式可读取 DeepSeek 官方历史消息接口，并为内嵌图片读取当前对话引用的图片地址。接口请求会复用站点登录态。「仅使用页面内容」控制历史消息接口通道，图片内嵌和页面滚动加载仍可能产生网络请求。详情见 [安全与隐私说明](SECURITY.md)。

1.5.8 的选择性导出依赖 DeepSeek 页面提供的虚拟消息编号。网页结构变化、图片跨域限制或历史内容加载失败都可能影响导出。请结合导出状态提示核对结果。插件由社区维护，与 DeepSeek 官方无隶属关系。

1.5.8 的消息选择控件定位样式位于深色模式媒体查询中，浅色模式下控件排列可能受影响。可在深色模式使用区间选择功能。

本次发布运行了仓库已有的长对话、区间选择、三格式和 DOM 提取测试。历史真实页面验证记录保留在下方及版本说明中。

## 一、文件目录结构

```
deepseek-md-exporter/                ← 插件本体（Edge「加载解压缩的扩展」时选这个目录）
├── manifest.json                    MV3 清单：零 API 权限，仅匹配 chat.deepseek.com
├── icons/
│   ├── icon16.png  icon32.png  icon48.png  icon128.png
└── src/
    └── content/
        ├── zip.js                   零依赖 ZIP 打包器（.docx 的容器格式 + base64 解码）
        ├── mermaid-capture.js       Mermaid 图表捕获：SVG → 本地栅格化 PNG（canvas）
        ├── image-extractor.js       用户上传图片：筛选 / 注册 / 滚动加载 / base64 转换（全本地）
        ├── md-parse.js              Markdown → 结构化块与行内片段（PDF / Word 共用）
        ├── html-to-md.js            HTML → Markdown 转换器（代码块 / 表格 / 公式 / 列表 / 引用）
        ├── markdown.js              组装 .md；空正文校验；时序自检
        ├── docx.js                  生成 Word（OOXML + PAGE/NUMPAGES 页脚页码）
        ├── pdf-doc.js               A4 分页排版 + 「第 X 页 共 Y 页」页脚 + 调用打印输出
        ├── api-extractor.js         接口数据解析（fragments 感知 + 深扫兜底 + 分支还原）
        ├── dom-extractor.js         页面抓取（正文根 / 用户气泡 / 思考块识别 / 图片占位标记，纯离线）
        ├── content.js               入口：按钮与面板、格式路由、双通道编排、诊断
        └── content.css              注入样式（dsmd- 前缀，深色模式适配）
```

文件职责是单向的：`html-to-md.js` 与 `markdown.js` 与 `api-extractor.js` 都是纯函数（不碰网络、可单独测试），`dom-extractor.js` 只读页面，只有 `content.js` 会发起（可关闭的）接口请求。

配套的离线测试工程在同级的 `deepseek-md-exporter-tests/`，不参与插件运行，安装时无需理会。

## 二、在 Edge 中安装（分步操作）

1. 打开 Edge，地址栏输入 `edge://extensions/` 回车。
2. 打开左下角的 **开发人员模式** 开关。
3. 点击 **加载解压缩的扩展**（Load unpacked）。
4. 在文件选择框中定位到 `deepseek-md-exporter` 目录（选中该文件夹本身，不要进入 `src`），点击 **选择文件夹**。
5. 列表中出现「DeepSeek 对话导出 Markdown」即安装成功。若显示为关闭状态，点一下开关启用。
6. 打开或刷新 `https://chat.deepseek.com` 的任意对话页，右下角会出现 **导出 MD** 蓝色按钮。

> 提示：安装后建议在 `edge://extensions/` 里关闭「允许访问文件 URL」（本插件不需要）。
> 升级版本时，点击该扩展卡片上的 **重新加载** 图标即可。

## 三、使用步骤

1. 打开 `https://chat.deepseek.com`，进入想导出的对话，等待消息加载完成。
2. 点击页面右下角的 **导出 MD** 按钮，弹出选项面板。
3. 在 **导出格式** 里选择 **Markdown / PDF / Word** 之一。
4. 按需勾选：
   - **排除所有思考过程**（默认勾选）：勾选后只保留你的提问和模型正式回复，自动过滤思考/推理区块；取消勾选则思考内容会写入对话中（Markdown 用「### 思考过程」区块，PDF/Word 用灰色缩进的思考段）。
   - **仅使用页面内容（不发送任何网络请求）**（默认不勾选，界面原文）：勾选后跳过历史消息接口通道。图片内嵌及页面滚动加载仍可能发出读取请求。不勾选时，插件可用当前登录态读取 DeepSeek 历史消息接口，补全超长对话内容。
5. 点击 **导出**，三种格式各自的表现：

   | 格式 | 结果 |
   | --- | --- |
   | **Markdown** | 直接下载 `对话标题_20260926-162013.md` |
   | **Word** | 直接下载 `对话标题_20260926-162013.docx`，页脚居中显示「第 X 页 共 Y 页」 |
   | **PDF** | 打开打印窗口，按面板提示：**目标选「另存为 PDF」→ 关闭「页眉和页脚」→ 保存** |

6. 导出完成后，面板状态区会显示消息条数、页数、数据来源——这些信息只显示在面板上，不写进文件。
7. 如果导出结果不符合预期，点击 **诊断**，会下载一份 `deepseek-export-diagnostic_*.json`，其中记录了页面结构识别结果与接口字段形状（不含完整对话内容），可用于定位问题。

> **PDF 的两个注意事项**
> 1. 打印窗口里的「页眉和页脚」必须**取消勾选**，否则浏览器会额外打上它自己的网址/页码，和本插件排好的页脚重复。
> 2. 想保留代码块底色，请在打印窗口勾选「背景图形」（不勾选也能正常阅读，只是代码块没有浅灰底）。

导出的 Markdown 结构（文件里只有对话本身，没有任何元数据）：

```markdown
# 对话标题

## User

你的提问（保留原有换行）

---

## DeepSeek

模型回复，代码块/表格/公式/列表按原格式还原

---

## User

下一个提问
```

顺序与网页端完全一致：从上到下就是对话发生的先后，每一轮里提问在前、回复在后。消息条数、正文字数、数据来源等信息只显示在插件面板上，不写入文件。

## 五、PDF / Word 导出与页脚页码（本次新增）

### 5.1 三种格式的关系

PDF、Word 与 Markdown **共用同一份内容**：都取自同一次提取（页面通道 + 接口通道择优）、同一套时序校正、同一个「排除所有思考过程」过滤。因此三种文件的消息条数、顺序、角色区分完全一致，只是渲染方式不同。

### 5.2 Word（.docx）

`src/content/docx.js` 直接生成 OOXML 包，不引入任何第三方库：

- 包结构：`[Content_Types].xml`、`_rels/.rels`、`word/document.xml`、`word/styles.xml`、`word/settings.xml`、`word/footer1.xml`、`docProps/*`，由 `src/content/zip.js` 以 ZIP 的 STORE（不压缩）方式打包 —— ZIP 规范允许不压缩，Word 正常打开。
- **页脚页码**：用 Word 自身的域 `PAGE` / `NUMPAGES` 实现，页脚段落 `jc=center` 居中，输出即「第 X 页 共 Y 页」，并随文档分页**自动更新**；`settings.xml` 里写了 `updateFields=true`，打开文档立刻显示正确页码，不需要手动按 F9。
- 正文：角色标题（User / DeepSeek）用加粗 + 主题色 + 下边框区分；标题、列表、代码块（Consolas + 浅灰底）、表格（真实 `w:tbl` + 边框）、引用、链接（真实超链接关系）分别映射到对应的 OOXML 结构。

### 5.3 PDF

PDF 由 **Edge 自身的打印引擎**输出，因此中文直接用系统字体渲染，**不需要下载或内嵌任何字体文件**（也就没有网络请求、没有额外权限）。真正的难点是页码，实现方式：

1. `src/content/pdf-doc.js` 先在离屏 iframe 里按 A4 排版：页面 210×297mm，左右边距 18mm，上边距 16mm，页脚区 14mm。
2. 逐块量高（`getBoundingClientRect` + 外边距），按内容高度 253mm 贪心装箱；超高的块会自动拆分：代码块按行拆、表格按行拆且每页重复表头、列表与引用按子元素拆；角色标题不会被留在页尾。
3. 分页确定后，把每页写成独立的 `.page` 容器（`page-break-after: always`），页脚写入**已经确定的**「第 X 页 共 Y 页」文本，再调用 `print()` 交给打印引擎。
4. 页码是排版阶段算出来的真实值，不依赖浏览器的页眉页脚设置 —— 这也是为什么要在打印窗口里关掉「页眉和页脚」，避免出现两套页码。

### 5.4 用户上传图片导出（1.1.0 新增）

用户在对话中上传给 DeepSeek 的图片现在会写进三种格式的导出文件；模型回复里的图片仍以 `[图片：说明]` 占位符呈现。

**识别与过滤**（`image-extractor.js` + `dom-extractor.js`）

- 只认用户消息气泡里的 `<img>`，按「尺寸 ≥ 64px + 自身与近祖无 avatar/icon/emoji/logo 等界面类名 + alt 非头像语义」排除头像、图标、表情、UI 装饰图；
- 图片在 Markdown 里的位置 = DOM 里的位置（文字与图片的相对顺序原样保留），全局按上传顺序编号为 `user-001.png`、`user-002.jpg` …；
- 只上传图片、没打字的「纯图片消息」也能识别为用户消息。

**读取与转换**（全本地）

- `blob:` 与同源 `https:` → `fetch` + `FileReader` 转 base64；
- 跨域图 → 先用 `crossOrigin=anonymous` 重取后经 `canvas.toDataURL`（服务器给 CORS 头即可成功），再试 `fetch`；都不行则**保留原始 URL 并标注「图片可能需联网查看」**——绝不为此新增 host_permissions，也绝不把图片交给外部服务；
- webp/bmp/svg 一律经 canvas 重编码为 PNG（Word 原生只认 png/jpeg/gif）；单图上限 30MB。

**三种格式的写入**

- **Markdown**：`![用户上传图片](data:image/png;base64,...)` 内嵌进对应用户消息位置；图片总量超过 16MB 自动改为打包 `.zip`（内含 `conversation.md` + `images/user-001.png` …，Markdown 用相对路径引用）；
- **PDF**：图片以 `<img>` 嵌入用户消息位置，等比缩放到版心内（宽 ≤ 版心宽、高 ≤ 110mm），整块参与分页、不跨页截断；页脚仍为排版阶段算定的「第 X 页 共 Y 页」；
- **Word**：图片作为 `word/media/*` 部件 + `<w:drawing>`（inline）嵌入用户消息位置（ImageRun 的等价实现）；页脚仍为 `PAGE`/`NUMPAGES` 域输出的「第 X 页 共 Y 页」，随真实分页自动更新。

**长对话与懒加载（1.5.0 强化）**：导出前先滚到消息容器底部、再回顶反复加载更早消息，随后**逐条消息与逐张上传图 `scrollIntoView`**，把 `loading="lazy"` / `data-src` 占位图强制切到真实地址，并等待全部上传图满足 `complete === true && naturalWidth > 0` 后才开始采集；采集结束后再恢复用户原来的滚动位置。转换阶段使用 4 路并发池、单图超时与重试，失败/超时/跨域无法内嵌的图片会进入失败清单，导出结束弹出「N 张用户图片未能导出」并在控制台列出 alt、原地址与所属角色，不再静默漏图。全程只操作本页滚动位置、只在本地读取图片。

**数据源说明**：图片只能来自页面 DOM。数据源选择接口通道（页面未渲染全部消息时）会把页面侧收集到的图片按「正文文本匹配 → 按用户消息顺序（优先尾部）对齐」贴回对应用户消息末尾；仍无法归属的图片进入失败清单并提示，不会无声消失。

### 5.5 Mermaid 图表导出修复（1.2.0 新增）

**故障**：DeepSeek 对话里 AI 生成的 Mermaid 流程图，导出 PDF / Word / Markdown 时得到的是源码文本（mermaid 源码、SVG 节点文字、内部 CSS），而不是渲染后的图形。

**根因**（两处叠加）：

1. 页面 DOM 里 Mermaid 是「源码块 + 渲染后的 SVG」并存，旧版把 `language-mermaid` 代码块当普通代码导出了源码；
2. 转换器用来跳过 SVG 的规则是大写 `'SVG'`，而 SVG 元素的 `tagName` 是**小写** `svg`——规则从未命中，于是 SVG 内部的节点文字与 `<style>` CSS 全被当正文漏出。

**修复**（`mermaid-capture.js`，新模块）：

1. **捕获**：导出时（滚动加载完成后）扫描页面上已渲染的 Mermaid SVG。识别用多信号：`class`/`id`/`data-lang` 含 "mermaid"、紧挨 `language-mermaid` 代码块的相邻 svg、形态过滤（≥120×60 且含 path/rect 等图形元素，排除图标）。
2. **栅格化**：把 SVG 序列化（补 XHTML 命名空间、显式宽高、2x 采样、白底）后经 `canvas.toDataURL` 转成 PNG——全程浏览器本地 API，零网络、零新权限。带 `foreignObject` 的 SVG 渲染失败时自动去掉文字标签重试，保证图形框架一定出得来。
3. **接入图片管线**：PNG 数据登记进图片注册表（`kind:'mermaid'`，与用户上传图同一套内嵌/打包/渲染机制）；正文转换时源码块与 SVG 两个位置用去重后的占位引用 `![Mermaid 图表](dsmd-img://N)` 替代，只输出一张图。
4. **三种格式**：Markdown 内嵌 `data:image/png;base64`（图片过多时随 zip 打包）；PDF 渲染为 `<img>`（限高等比、整块换页）；Word 写入 `word/media/mermaid-001.png` + `<w:drawing>`。均显示完整图形，不再出现代码文本。
5. **接口通道**：接口数据里仍是 ```mermaid 围栏，按源码匹配换成已捕获的图片引用；匹配不上（页面没渲染该图）时保留源码围栏——宁可给代码也不丢内容。

未捕获到渲染图时 Mermaid 仍按源码围栏导出（与旧行为一致，不丢内容）。

### 5.6 分支跟随导出修复（1.3.0 新增）

**故障**：DeepSeek 支持「修改同一提问」生成多个对话分支。旧版只能导出最后一次修改生成的分支；用户在页面上切换到旧分支后导出，得到的仍是最新分支的内容。

**根因**（两处叠加）：

1. 接口（`history_messages`）返回的是**全部分支**的消息合集，其 `current_message_id` 只指向**最新生成的叶子**，不会跟随页面上的分支切换——旧逻辑从该叶子回溯，于是永远拿到最新分支；没有游标时退回时间排序，还会把多个分支按时间交错混在一起。
2. 通道选择规则是「接口消息数 > 页面消息数就采用接口」——分支对话的接口合集必然比页面（单分支）多，于是分支对话几乎总是走了错误的接口数据。**页面显示哪个分支，只有页面自己知道。**

**修复**（`api-extractor.js` + `content.js`）：

1. **分支指纹**：导出时先从页面提取结果算出「当前显示分支」的指纹——依序的（角色，正文比对键）。比对键做了归一化：抹平硬换行反斜杠、图片/图表占位引用、围栏代码块（页面侧 mermaid 源码已替换为图片引用），使页面文本与接口 Markdown 能稳定对上。
2. **全树搜索最优分支**：接口解析不再盲目从 `current_message_id` 回溯，而是对消息树**每条根→叶路径**与指纹打分（有序匹配数），取最高分；同分时按「会话游标指向的叶子 → 时间更新 → 路径更长」裁决。用户切到哪个分支，接口就只返回那条分支。
3. **可靠性门槛与回退**：指纹命中数与路径长度不足（如指纹完全对不上、没有 `parent_id` 的扁平载荷）时，自动回退到原有游标回溯/时间排序逻辑，绝不空手而归。
4. **通道选择改为「页面分支无条件优先」**：只要页面通道可用就用页面数据；接口只有在**按指纹完整命中同一分支**且比页面更完整（页面没渲染出早前消息）时才被采用。Markdown / PDF / Word 三条格式共用这一份消息，行为完全一致。
5. **兼容既有能力**：图片回贴（按文本匹配用户轮次）与 Mermaid 围栏替换（按源码匹配）都在「同一分支」的消息上进行，分支修复让它们更准确；面板与诊断报告会显示分支指纹命中情况（`matched/fingerprintSize` 与策略）。

安全边界不变：不新增任何权限，不向任何第三方发送数据，所有解析与生成本地完成。

### 5.7 三格式还原度修复与分支序号排版（1.4.0）

以「原始界面截图 + MD/PDF/Word 对照样本」逐项审计后修复（`audit.test.js` 固化回归）：

1. **分支序号排版**：页面上消息右上角的「1 / 2」版本指示，旧版会被误判成独立用户消息，导出为正文下方的「## User / 1 / 2」空段。现改为：识别为切换器 → 按纵向位置（无布局时按文档序）关联到所属消息 → **统一写在角色标题同一行右侧**——Markdown 为 `## User（1 / 2）`，PDF 为角色行内右浮灰字，Word 为角色段右对齐制表位。接口通道的消息按「同父同角色兄弟数 + 时间序」计算同样序号。
2. **嵌套列表成对重复**（三格式同源）：`convertList` 的克隆移除谓词拿「原始嵌套 UL」与「克隆后 UL」比较，永远不命中，子列表从未移出克隆体，被转换两遍。修复后子列表只输出一份；另加「同内容子列表去重 + 相邻重复行收口」两道保险。
3. **PDF 列表符号消失**：旧版 marker 靠 `text-indent:-3.2mm` 悬挂，被 `.page-body` 的 `overflow:hidden` 整块裁掉（HTML 里有、打印不可见）。现改为 marker 绝对定位在 padding 区内，`-`/`1.` 全部可见。
4. **列表层级缩进**：旧版每级仅 0.7mm（PDF）/ 20 twips（Word），肉眼不可辨。现统一按「每 2 空格 = 一级」，PDF 每级 4.5mm、Word 每级 360 twips。
5. **公式渲染**（PDF/Word）：旧版直接输出 `$E = mc^2$`、`$$\sum…$$` 等 LaTeX 源码。现新增行内/块级公式解析与 `mathToText` LaTeX→Unicode 转换（`rac` → 分式、`^2` → ²、`\int_0^1` → ∫₀¹、`\sum` → Σ、希腊字母/运算符全表），PDF 行内斜体衬线、块级居中；Word 斜体文本、块级独立居中段。Markdown 仍保留 `$…$` 源码（由 MD 渲染器处理）。
6. **引用行尾反斜杠泄漏**（PDF/Word）：Markdown 硬换行 `\` 在渲染层泄漏为可见字符。现解析引用时剔除，Markdown 中保留（合法语法）。
7. **PDF 标题孤悬页尾**：「3. 表格」这类标题会单独留在页尾、表格在下一页。装箱算法现在把页尾的角色标题与各级小节标题（keep 块）整体带到下一页。

其余项目（表格边框/表头跨页重复/对齐、代码块语言标签与底色、行内样式、emoji、超链接、硬换行）经审计确认三格式均已正常，未做改动。

### 5.8 用户上传图片导出修复（1.4.1）

**故障**：所有场景（单轮单图、单轮多图、多轮各带图、多轮穿插）的用户上传图都导不出来，三种格式一致；而模型生成的图（Mermaid）不受影响。

**根因**：DeepSeek 把上传图渲染在**文字气泡之外**的附件容器里，气泡只包住右侧那段文字。旧实现只在「文字气泡」内部找 `<img>`，由此有两种失效形态：

1. 附件容器本身也满足「右侧窄块」特征 → 被单独识别成一条「纯图片」用户消息：图片和文字被拆成两条，顺序也乱（体积小的图看起来像"没导出来"）；
2. 附件容器更宽、不满足气泡特征 → 根本不会被识别，图片全部丢失（这就是"全部失效"的主因）。

**修复**（`image-extractor.js` + `dom-extractor.js`）：

1. **纯图片容器并回同一轮**（`pairImageBubbles`）：把「只有图、没有字」的候选按共同祖先（同属一轮且不含模型正文）配回该轮的文字气泡，不再单独成条；真正"只发图没打字"的消息找不到可配气泡，仍保留为独立用户消息。
2. **按轮次范围收割**（`harvestTurn` + `userImageScope`）：收割范围从气泡扩到「本轮用户行，并向上扩到仍只包含这一轮用户内容的最大祖先」，覆盖文字气泡之外的附件容器；气泡内的图按原位置替换，气泡外的图按**文档先后**分 `before`/`after` 两组拼到正文首尾（附件在文字上方，就排在文字之前），保证排列顺序与对话时序一致。
3. **补充信号**：除 `<img>` 外，还识别用 `background-image` 呈现的缩略图（按尺寸 + 类名过滤），避免换一种渲染方式又漏图；头像/图标/表情继续按尺寸与类名排除。
4. **可诊断**：诊断报告新增 `imageScan`（页面图片总数、识别为上传图的数量、被过滤项的类型/尺寸/地址协议），上传图再次出问题能直接定位是"没识别"还是"读取失败"。
5. **三格式统一**：图片统一进入图片注册表（`user-001.png`…），Markdown 内嵌 data URI（总量超限自动打包 zip）、PDF 渲染为 `<img>`、Word 写入 `word/media/*` + `<w:drawing>`；与 Mermaid 图表、排除思考过程、页脚页码、分支序号等既有能力共用同一条管线，互不影响。

### 5.9 长对话多图漏图修复（1.5.0）

**故障**：短对话（≤5 轮、≤3 图）正常；对话 ≥20 轮、用户上传图 ≥10 张时，Markdown / PDF / Word 会同时少掉若干张图，且导出提示成功、不报错。Mermaid 不受影响。

**根因**：不是「识别不到图片」，而是采集时机与采集完整性：

1. **懒加载未触发**：长对话中未进入过视口的图片 `src` 仍为空或是 1×1 占位图，真实地址在 `data-src`/`data-original` 里；旧逻辑要求 `<img>` 已有 `src`，这些图直接被当成非上传图跳过，既不导出也不留失败记录。
2. **滚动预加载不完整**：旧实现只反复回顶 + 自上而下粗扫，顶部加载循环可能耗尽 40 秒预算，中段和尾部消息从未进入视口；结束后立即恢复滚动位置，懒加载图没机会完成。
3. **转码失败被吞**：`fetch` 没有超时、`catch` 后只把状态改成 remote/failed，UI 仍显示成功；长对话下部分请求超时/失败时用户完全无感。
4. **图片与消息脱钩**：消息范围/附件容器没覆盖到的图片不会出现在注册表里，因此三种格式同时缺同一批图。

**修复要点**：

1. **全量预加载**（`ensureHistoryLoaded`）：先滚到底 → 回顶反复加载历史（只占 40% 预算）→ 逐条消息和逐张上传图 `scrollIntoView` → 再到底；`loading=lazy` 强制改 `eager`，`data-src`/`data-original`/`srcset` 占位图写回真实 `src`。
2. **等待就位**（`waitForUploadImages`）：只有 `complete === true && naturalWidth > 0` 才算加载完成；无地址/已报错的图不空等，交给转换阶段记入失败清单。采集结束才恢复原滚动位置。
3. **并发池 + 超时 + 重试**（`convertAll`）：4 路并发、单图 20s 超时、失败自动重试 2 次；失败项保留 `failureReason` 与 alt/src/role 元数据，不再静默吞掉。
4. **归属兜底**（`bindOrphanUploads`）：按轮次范围收割后仍未被认领的上传图，按元素包含/视觉距离/文档顺序补到最近用户消息；确实无法定位的进入 `unboundImages`，以失败提示上报。
5. **失败可见**：导出结束若 `failed/remote/unbound > 0`，弹出「N 张用户图片未能导出」，面板保留红色提示，控制台输出 alt、原 src、所属角色与失败原因；三种格式共用同一份失败清单。
6. **三格式一致**：Markdown / PDF / Word 都由同一份预处理消息 + 同一个图片注册表渲染；Word 图片最大宽 600px 等比缩放，PDF 图片块补 `page-break-inside: avoid`。

## 六、安全设计说明

**权限：只申请必要的，一个多余的都没有。**

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| `permissions` | `[]` | 没有申请 storage、tabs、downloads、scripting、webRequest 等任何 API 权限 |
| `host_permissions` | `[]` | 未声明独立主机权限 |
| `content_scripts.matches` | `https://chat.deepseek.com/*` | 生效范围仅此一个域名，其他网站不会被注入 |
| 后台脚本 | 无 | 没有 service worker，不存在后台静默任务 |
| `web_accessible_resources` | 无 | 不向页面暴露任何扩展资源 |

新增 PDF / Word 导出**没有增加任何权限**：Word 是本地拼装 zip + XML，PDF 走浏览器自带的打印引擎，两者都不需要新权限，也不下载任何字体或第三方库。1.1.0 新增的图片导出同样零新增权限：图片 base64 由 `fetch` / `FileReader` / `canvas`（浏览器标准 API）在页面内完成，读取的对象仅限当前对话页里已显示的图片地址本身。

Edge 在扩展详情页会显示本插件「可读取和更改 chat.deepseek.com 上的数据」——这是注入界面按钮所必需的最小主机范围，除此之外没有任何权限。

**数据处理与网络读取。**

- 对话内容的解析、Markdown 生成、文件下载全部在页面内完成，文件通过 Blob 直接落地，不经过任何服务器。
- 未勾选「仅使用页面内容」时，可对 `https://chat.deepseek.com/api/v0/chat/history_messages` 发起只读 GET，复用当前登录态。图片内嵌还会读取当前对话引用的图片地址，可能涉及 DeepSeek 文件服务或图片来源站点。该选项仅控制历史接口通道。
- 不收集身份信息、浏览记录、使用数据；无埋点、无广告、无远程代码、无 CDN 依赖。
- 代码里没有 `eval`、没有远程脚本加载，所有逻辑都是本仓库源码。
- 选项偏好保存在该站点当前浏览器配置的 `localStorage`（键名 `dsmd_exporter_prefs_v1`），可通过清除站点数据移除。接口通道还会读取 `userToken`，用于对 DeepSeek 官方历史消息接口进行认证。

**界面隔离。** 所有样式类名统一 `dsmd-` 前缀并对关键属性加 `!important`，不修改页面任何既有元素的样式；注入节点只有右下角一个按钮和面板，卸载插件即彻底消失。

## 七、「导出只有 User / DeepSeek 身份标题、没有正文」的原因与解决方案

### 7.1 故障现象与原因

原版插件导出时，文件里有 `## User` `## DeepSeek` 标题和分隔线，但正文一片空白。

根因是**内容字段变了**：DeepSeek 已把助手消息的正文从顶层的 `message.content` 迁移到 `message.fragments[]` 数组里，形如：

```json
{
  "message_id": 2,
  "role": "ASSISTANT",
  "fragments": [
    { "type": "THINK",    "content": "先讲分治思想……" },
    { "type": "RESPONSE", "content": "快速排序是一种分治算法……" }
  ]
}
```

旧实现只读 `message.content`，取到 `undefined`，于是「输出标题」这一步照常执行、「输出正文」这一步静默跳过 —— 结果就是有骨架没内容。上游项目也记录了同类报告（issue #8：TXT 导出「有结构、无内容」，作者推测是接口变更）。这类问题的本质是**把未公开接口的字段命名当成了稳定契约**。

### 7.2 本插件的解决方案

**① 双通道，主从互补，任一通道可用就不会导出空文件**

- **页面抓取通道（首选、纯离线）**：直接读取当前页面已渲染出来的内容。它不依赖任何字段命名，读到的就是用户亲眼所见的内容。识别不靠随机哈希类名，而是靠稳定的结构信号：DeepSeek 的 Markdown 渲染根节点固定带 `ds-markdown` 类；用户消息用布局特征判定（气泡宽度小于列宽且紧贴右侧 = 用户，模型回复占满整列宽）。可选传 `data-role="user"` 等显式标记时优先采用。
- **接口通道（补全）**：解析历史消息接口，用于页面因超长会话未渲染全部消息时补全。两通道都可用时，比较消息条数与正文总字数，取更完整的一份，并在面板中如实告知数据来源。

**② 接口解析对字段变化免疫**

- 按 `fragments` 的**类型**分流而非按字段名取值：`THINK` 类片段进思考过程，`RESPONSE` 类片段进正文，检索/工具类片段进「附加内容」；没有 `type` 的片段一律按正文处理（宁可多留，绝不丢掉）。
- 顶层旧字段 `content` / `thinking_content` / `text` / `answer` 等继续兼容；两类来源内容重复时自动去重。
- 前两步都取不到正文时，**深扫整条消息对象**，取其中最长的有效文本兜底，并排除 id、状态枚举（`FINISHED`）、时间戳、哈希等噪音字段。
- 分支还原优先按 `current_message_id` + `parent_id` 回溯当前分支（正确处理「重新生成」留下的旧回答），元数据缺失或链路断裂时退回按时间排序，两种情况都不会返回空数组。
- 还兼容了 `{request_message, response_message}` 轮次包装、`role` 大小写混乱、`content` 为嵌套对象或数组等形态。

**③ 从产品层面禁止空壳文件**

即使两条通道都异常，也不会生成一个只有标题的文件：

- 组装前逐条校验，**正文与思考过程都为空的轮次直接丢弃**；勾选「排除思考过程」时，只有思考没有正式回复的轮次整条丢弃。
- 若全部轮次都被丢弃，导出**判定为失败**，面板给出可读原因（并提示可用「诊断」导出报告），而不是写出一个空文件。
- 页面通道识别到的消息节点里取不到文本时，同样判为失败并说明原因。

**④ 可诊断、可维护**

任何一次导出失败都能点「诊断」拿到结构报告（正文根数量、命中的用户气泡及命中依据、思考块、接口字段形状）。DeepSeek 前端改版导致识别失效时，改动集中在 `dom-extractor.js` 顶部的几组选择器与判定规则，不需要动其他文件。

## 七点五、图片导出验证步骤（可手工执行）

1. **准备对话**：在 chat.deepseek.com 新建一段包含以下内容的对话——
   第一条：文字 + 上传 1 张图片（问「这张图里是什么」）；
   第二条：只上传 1 张图片、不输入文字；
   第三条：普通文字提问，并开启深度思考让模型产生思考过程。
2. **导出 Markdown**：勾选「排除所有思考过程」→ 导出。打开 `.md` 检查：
   - `## User` 段内出现 `![用户上传图片](data:image/png;base64,...)`，位置与网页端一致（文字在前图片在后按原顺序）；
   - 纯图片消息的 `## User` 段只有图片引用、没有空段报错；
   - 文件里没有思考过程区块、没有导出时间等元数据；User 在前、DeepSeek 在后。
3. **导出 PDF**：打印窗口「目标=另存为 PDF、关闭页眉和页脚、勾选背景图形」→ 保存后检查：
   - 两张图片出现在对应用户消息的位置，等比缩放、无跨页截断；
   - 每页页脚居中「第X页 共Y页」，页码与总页数一致；思考过程未出现。
4. **导出 Word**：打开 `.docx` 检查：
   - 图片内嵌（文件大小明显变大），位于对应用户消息处，双击可查看；
   - 页脚居中「第X页 共Y页」，多页打印/转 PDF 后页码正确（PAGE/NUMPAGES 域随真实分页更新）。
5. **取消勾选「排除所有思考过程」重新导出**：三种格式都应出现灰色思考区块，且图片仍然保留在用户消息中。
6. **回归确认**：换一段没有图片的旧对话，三种格式导出结果与 1.0 行为一致（`images.test.js` 中的「无图片对话」用例即对此的自动回归）。
7. **跨域降级确认**：若某张图片在导出文件里显示为原始链接 + 「图片可能需联网查看」，说明 DeepSeek 的图片服务器未放行跨域读取——这是预期降级，不是故障（可看插件面板的图片统计：内嵌 / 需联网查看 / 加载失败）。

自动化：`npm test`（含 `images.test.js` 53 项）+ `npm run artifacts` 生成带图样本后用 `python-docx` / Chrome 打印引擎复验。

## 八、Edge 兼容性说明

| 项目 | 说明 |
| --- | --- |
| 目标浏览器 | Microsoft Edge（Chromium 内核），Manifest V3 |
| 最低版本 | Edge 105+ 即可完整使用（2022 年 9 月起的正式版）。当前主流正式版（120+）全部支持 |
| 用到的新语法 | 内容脚本里用了 `?.`／`??`（Edge 80+）、正则后行断言 `(?<!…)`（Edge 62+）、`String.replaceAll` 系列未使用；样式里用了 `:has()` 让选中的格式高亮（Edge 105+，低版本只是不高亮，功能不受影响） |
| 下载方式 | Markdown / Word 用 Blob + `<a download>`，不依赖 `downloads` 权限；PDF 用打印引擎，不依赖任何权限 |
| 图片相关 API | `fetch`（blob:/同源/带 CORS 的跨域图只读 GET）、`FileReader`（Blob → data URL）、`Image` + `canvas.toDataURL`（跨域读取与 webp→PNG 重编码）——均为 Chromium 标准 API，Edge 105+ 全部支持 |
| PDF 输出路径 | Edge 打印窗口 → 目标选「另存为 PDF」（也可用「Microsoft Print to PDF」打印机）；Chromium 打印引擎自带中文渲染，无需字体文件 |
| Word 兼容性 | 生成的是标准 OOXML（Word 2007+ 格式），Word、WPS、LibreOffice 均可打开；页脚页码为 Word 原生域，会随分页自动更新 |
| 深色模式 | 插件面板跟随系统深色模式；导出的文件一律白底黑字，保证打印与阅读效果 |
| 已知限制 | PDF 需要用户在打印窗口点一次「保存」（浏览器不允许脚本静默导出 PDF，这是安全边界，插件无法也不应绕过）；跨域图片若服务器不给 CORS 头则只能保留原始链接（浏览器不允许内容脚本读取跨域像素，插件不会为此新增权限） |

## 九、常见问题

**导出只有模型回复，没有我的提问？**
页面通道若没识别到用户气泡会照常导出并在面板提示。请确认消息渲染完成（向上滚动到底部），或取消勾选「仅使用页面内容」让接口通道补全。若反复出现，请用「诊断」导出报告。

**超长对话导出不完整？**
长会话页面可能只渲染了部分历史消息。取消勾选「仅使用页面内容」后重试；插件会对比两条通道，采用更完整的一份并提示来源。也可先向上滚动让消息加载完再导出。

**点导出没反应/没下载？**
检查 Edge 是否拦截了下载（地址栏右侧下载图标），以及扩展是否被停用。导出过程与结果都会显示在面板状态区。

**代码块里的语言标签或「复制」字样混进内容？**
插件已专门处理：语言名从代码块横幅中提取，「复制/重新生成」等界面文字在转换前被摘除，横幅被塞进 `<pre>` 内部的情况也会清理。

**会不会把我还没看到的思考过程一起导出去？**
思考过程默认被排除（面板首个勾选框默认勾选）。只有你主动取消勾选时才会写进文件。

**我修改过提问、对话有多个分支，导出的是哪个分支？**
导出你在**页面上当前显示**的那个分支。切换分支后直接点导出即可；导出的内容与页面所见一致。若某条分支在页面上没有渲染出早前消息，插件会按当前分支指纹从接口补全同一分支的内容（面板会标注「当前显示分支」）。

**导出的顺序和网页上不一样？**
插件按元素在页面上的实际纵向位置排序，理论上与网页端所见一致；同时会识别 `column-reverse` 这类反向布局，并在组装完成后做一次时序自检（倒序会自动翻转回来）。若仍遇到顺序异常，请用「诊断」导出报告，其中的 `orderMode` 字段会显示本次采用的排序依据（`visual` = 按页面位置，`document` = 按文档顺序）。

**文件里为什么没有导出时间、消息数这些信息？**
按需求已全部移除，文件只保留对话正文。这些信息仍在插件面板的状态区显示，方便你确认导出结果（如需重新加回，改 `src/content/markdown.js` 的 `buildMarkdown` 即可）。

**上传的图片在导出文件里不见了？**
插件会从「整轮用户消息」范围（不只是文字气泡）收集图片，单张/多张/多轮都支持，头像与图标会被排除。若仍缺失，请点「诊断」查看 `imageScan`：`uploads` 为 0 说明页面结构未被识别，`images` 里的 `remote` 数量说明图片读取失败（跨域图片无法本地读取时会保留原地址并标注）。

**Mermaid 图表导出后是代码不是图？**
请确认导出前图表已在页面上渲染完成（滚动到图表位置能看到图形）。插件会把已渲染的图表自动转为 PNG 嵌进三种格式；若某张图在页面里从未渲染（超长对话未加载到），对应位置会保留 Mermaid 源码围栏，可先在页面上把消息加载出来再导出。

**PDF 导出后页码不对/出现两套页码？**
打印窗口里的「页眉和页脚」必须取消勾选（那是浏览器自己加的），本插件的「第 X 页 共 Y 页」是排版阶段算好的，位于页脚居中位置。若页码位置偏上或偏下，检查打印窗口的「边距」是否被改成了自定义值，恢复为「默认」即可。

**Word 打开后页脚页码显示为「第 1 页 共 1 页」不动？**
页码是 Word 的域，正常会自动更新（文档已设置打开即刷新）。若显示的是缓存值，在 Word 里按 `Ctrl+A` 再按 `F9` 手动刷新一次即可。

**我上传的图片会导出吗？**
会。Markdown 默认 base64 内嵌（总量超 16MB 自动打包 .zip），PDF / Word 嵌入对应用户消息位置并等比缩放。跨域图若 DeepSeek 的图片服务器不给 CORS 头，则保留原始链接并标注「图片可能需联网查看」——这是浏览器安全策略的边界，插件不会为读取图片新增任何权限。

**轮次之间的 `---` 分隔线可以去掉吗？**
（仅影响 Markdown 文件）
可以：删掉 `src/content/markdown.js` 中 `buildMarkdown` 里那一行 `lines.push('---')`（位于每轮末尾），重新加载扩展即可，正文格式不受影响。
